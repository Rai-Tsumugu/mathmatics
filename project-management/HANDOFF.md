# 開発引き継ぎ書

最終更新: 2026-08-01

## 1. プロジェクトの目的

大学数学の各単元を前提関係で結び、難しい数式や問題を段階的に解けるようにする
学習サービスを構築する。各単元には、講義、インタラクティブ教材、問題集、
解答解説を用意する想定である。

現在は教材本文より先に、次の基盤を整備している。

- ツリーフローをホーム画面として表示する
- ツリー上の単元から関連ページへ相互に移動できるようにする
- 共通UIと単元別コンテンツを分離する
- 学習者の進捗と、開発者の制作進捗を別々に管理する
- VercelでホスティングできるNext.js構成にする
- 作問・難易度・レビュー工程を管理する画面を用意する

### 開発サーバーとビルドを同時に動かさない

`next dev` を起動したまま `npm run build` を実行すると、同じ `.next` ディレクトリを
奪い合い、ビルドが分単位でハングする。実測で17分かかった例がある。
ビルド前に開発サーバーを停止すること。

また、開発サーバーは起動時点のキャッシュを配信し続けるため、教材ファイルを更新しても
ブラウザに反映されないことがある。教材の描画確認は、ビルド成果物
`.next/server/app/learn/<unitId>.html` を直接見るのが確実である。

## 4. データとファイルの責務

### ツリー構造

`tree-map/math-treemap-full.html` が単元と依存関係の正本である。

`npm run content:sync` を実行すると、`scripts/sync-treemap.mjs` が次を同期する。

- `src/content/tree.generated.json`
- 未作成の単元別教材フォルダと雛形
- `src/content/admin-data.json` の初期データ（ファイルが存在しない場合のみ）
- `project-management/progress.md` の初期工程表（ファイルが存在しない場合のみ）

既存の教材ファイル、管理データ、工程表は同期処理で上書きしない。

### 学習者の進捗

ホーム画面の単元カードで操作する進捗は、ブラウザのローカルストレージへ保存する。
これは学習者ごとの端末内データであり、管理画面の制作進捗とは別物である。

### 教材本文のフォーマット規約

教材Markdownは `src/lib/content.ts` がビルド時に読み、KaTeX付きHTMLへ変換する。
規約は次のとおりで、`npm run content:check` が機械検査する。

- 先頭にYAML frontmatter（`title` / `status` / `updated`）を置く
- `status` は `未着手` / `作業中` / `レビュー中` / `完了`。`未着手` の教材は描画されず、
  ページ上は「準備中」表示になる。frontmatterを持たない旧雛形も同じ扱い
- 本文の見出しは `##` から開始する。`#`（h1）は使わない。単元名はページ側が出す
- 数式はKaTeX構文。インライン `$...$`、ブロック `$$...$$`
- 生HTMLは `<details><summary>` のみ使用可（段階的ヒント用）。前後に空行が必要
- **GFM表のセル内で絶対値記号に生の `|` を使ってはならない。** `\lvert` / `\rvert`
  を使う。生の `|` は列区切りと解釈され、表が崩れて配点などが消滅する。
  ビルドも型チェックも通ってしまうため目視でしか気づけない
- `problems.md` の `## 問題 N` と `solutions.md` の `## 問題 N の解答` は番号を一致させる

解答解説は既定で閉じた `<details>` に格納され、先に答えが見えないようにしてある。

### 難易度判定と採点ステップ

`project-management/difficulty-standard.md` が正本である。主な内容は次のとおり。

- 6軸（前提概念の数・解法選択の自由度・式変形の長さ・抽象度・誤答しやすさ・想定所要時間）
  の加重平均と、5つの上書き規則によるLevel算出
- 推定難易度と実測難易度の区別、実測値の合成式
- 証明型・多段階の応用問題に対する**採点ステップ**（途中点）の設計規約
- ステップ別到達率から前提単元グラフへフィードバックする手順

Level算出は `src/lib/difficulty.ts` に実装済み。重みと閾値は基準書の節番号付きで
定数化してある。**基準書を改訂したらこの定数も追従させること。**
境界±0.10のグレーゾーン判定は人間の判断を要するため意図的に未実装である。

採点ステップの表は6列で書く。`dif` の `workbook/solutions.md` が実例である。

```
| # | 小問 | 関係 | 到達判定 | 配点 | 対応するヒント |
```

「関係」は直前ステップとの関係で、`起点` / `直列` / `独立` の3値をとる。
**繰り上げ到達（前段を飛ばした答案を到達扱いにする処理）は `直列` の間でのみ適用する。**
`起点` は前段が存在しないため、`独立` は前段はあるが論理的含意が切れているため、
いずれも繰り上げの対象外となる。

この区別は必須である。所属小問で代用してはならない。`dif` の問題7のように、
同じ小問の中に独立なステップが並ぶ問題が存在するためである。同問では
「ロピタルの適用可否の判断」と「極限値の算出」が直交しており、後者だけに到達する答案
（別手段で極限を出す答案）のほうが多い。小問境界で繰り上げると、この問題の到達目標が
測定されないまま満点として記録される。

「判断」と「算出」が直交する構造は多くの単元に現れる。収束判定と極限値、
対角化可能性の判定と対角化行列、分布の同定と期待値・分散、可積分性の判定と積分値などである。

6軸の素点は `ProblemRecord.difficultyAxes` に保存できる（任意フィールド）。
管理画面に入力UIはまだ無いが、JSONへ手書きした値は保存操作で失われない。

### 制作側の進捗・問題データ

管理画面のデータは `src/content/admin-data.json` に保存する。
型定義は `src/lib/admin-types.ts`、読み書きと検証は
`src/lib/admin-store.ts` が担当する。

開発環境では管理画面の「変更を保存」からJSONを更新できる。本番環境では
Vercelのファイルシステムを永続保存先にできないため、意図的に読み取り専用にしている。

### 工程管理表（正本の役割分担: 2026-07-29 決定）

二重管理を解消するため、正本を次のとおり分担する。

- **全体工程・リリース判定・執筆順の正本**: `project-management/progress.md`（人が直接更新）
- **単元・問題・レビューの制作状態の正本**: `src/content/admin-data.json`（管理画面から更新。
  型検証が効くため、状態変更はこちらを先に更新する）
- `progress.md` の単元別表は**概況ビュー**とする。単元の完了など節目にのみ手動で反映し、
  日々の状態変更は追わない。将来はスクリプトで `admin-data.json` から自動生成し、
  手動更新を全体工程のみに縮小する（工程 P17）。

## 6. 管理画面の設計

管理画面は次の4画面をクライアント側で切り替える。

1. 概要
   - 教材完成数
   - 問題数
   - レビュー待ち件数
   - 分野別進捗
   - 難易度分布
2. 単元管理
   - 講義、インタラクティブ、問題集、解答解説の制作状態
   - 担当者、期限、公開状態、制作メモ、参考資料
3. 問題バンク
   - 問題文、答え、完全解説
   - 推定難易度、実測難易度、問題形式、想定時間
   - 必要スキル、前提単元、ヒント、よくある誤答
4. レビュー
   - 作問済み、数学レビュー、UI確認、公開可能、公開済みの工程
   - レビュー担当とコメント
   - 差し戻しとバージョン更新

問題IDは関連参照が壊れないよう、作成後は画面から変更できない。
保存前には、57単元の存在、各状態値、問題IDの重複、難易度範囲などを検証する。

## 7. 重要な設計判断と注意点

- 単元や依存関係を直接 `tree.generated.json` へ追加しない。原案HTMLを更新して同期する。
- 自動同期スクリプトは既存教材を上書きしない方針を維持する。
- 共通レイアウトやデザインを単元別ファイルへ複製しない。
- 学習者進捗と教材制作進捗を混同しない。
- Vercel上でローカルJSON書き込みを有効にしない。永続化にはDBが必要。
- 問題の「推定難易度」は作問者の仮説であり、正答率、所要時間、ヒント使用率などから
  得る「実測難易度」と区別する。
- AIによる作問をそのまま公開しない。最低でも数学レビューと表示確認を通す。
- Git管理の方針は決定済み（8-B節）。**公開リポジトリに教材本文と管理データを
  含めてはならない。** コミット前に `.gitignore` の除外対象を必ず確認する。
- **難易度判定基準書は確定した仕様ではなく、教材制作と往復しながら育てる文書である。**
  `dif` を作る過程で基準書は3回改訂された（途中点方式の導入、規則の優先順位の明記、
  小問単位の型判定と規約5'）。いずれも机上では気づけず、実際に問題を採点ステップへ
  落として初めて表面化した。残り56単元でも同様の改訂が起きると想定すること。
  特に線形代数系（証明の構造が異なる）と確率統計系（計算と解釈が混在する）で
  新たな穴が出る可能性が高い。
- **AIが書いた教材を、数学レビューを通さずに確定しない。** `dif` では2巡のレビューで
  致命的な誤りが1件見つかった。導関数の不連続点の分類で、講義側は正しく書かれていたのに
  解答側だけが誤っており、単独のファイルを読むだけでは検出できない種類の誤りだった。
- **査読者が提示した修正案をそのまま適用しない。** 査読案は解答の要旨から起こされるため、
  本文の実際の記述とずれることがある。`dif` では査読案どおりに書くと、教材自身が
  「典型的な誤答」として挙げている手順違反の答案が満点になる採点ステップができていた。

### C. 執筆順（2〜6単元目・決定済み）

各単元は「テンプレートと基準書の検証」を兼ねる。順序と狙いは次のとおり。
